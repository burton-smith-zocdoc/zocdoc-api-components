# ADR-001: When to write an ADR

Write an Architecture Decision Record when making decisions that:

- **Affect multiple packages or consumers** — changes to the config API, event contracts, or component hierarchy
- **Are difficult or costly to reverse** — dependency choices, breaking the standalone-capable pattern
- **Involve trade-offs that future readers might question** — "why didn't they just use context?"
- **Establish patterns others should follow** — new conventions, composition approaches

**Do write an ADR for:**

- Changing how components communicate (e.g., adding context protocol)
- Adding a new Charm base class dependency
- Changing the token/prefix configuration approach
- Deciding between competing implementation approaches with meaningful trade-offs

**Don't write an ADR for:**

- Bug fixes
- Adding a new component that follows existing patterns
- Refactors that don't change behavior
- Minor dependency updates

When in doubt, ask: "Will someone six months from now wonder why we did this?" If yes, write an ADR.
