# Primitives Reference

`@powered-by-zocdoc/primitives` provides Zocdoc-styled Charm UX components with the `zd-` tag prefix.

## Critical: Import Order

The package configures the `zd-` prefix on import. Always import primitives before using any component:

```typescript
import { ZdButton, CharmElement } from '@powered-by-zocdoc/primitives';
```

**Never import Charm barrels directly** (e.g., `@charm-ux/core/components/button/index.js`). Import from `@powered-by-zocdoc/primitives` or from class modules.

## Using in Templates

Write `<scoped-*>` inside `this.html` and declare the class in `dependencies()`.
`CharmElement` rewrites the tag to the registered prefix as it renders, so nothing
is interpolated and no prefix is typed (PBZD-003):

```typescript
public static override get dependencies(): (typeof CharmElement)[] {
  return [ZdButton];
}

protected override render() {
  return this.html`<scoped-button variant="primary">Submit</scoped-button>`;
}
```

The base name after `scoped-` is the primitive's tag minus `zd-`:
`ZdRadioGroup` → `<scoped-radio-group>`.

**A `<scoped-*>` missing from `dependencies()` renders an undefined element** —
no error, no warning, an empty box. This is the most common failure in the
package, so check the two together.

`scope.tag()` exists for tag names needed as a *string* (a `querySelector`, a test
helper). Not for markup — `lit/static-html.js` is imported nowhere in this repo.

## Reading This Package Efficiently

Every component follows the same shape, so most files tell you nothing you can't
infer. Read the exceptions, not the pattern.

**Don't read these files** — they are large and answerable by grep:

| File | Size | Instead |
|------|------|---------|
| `TOKENS.md` | ~2900 lines, ~45k tokens | `grep -A25 '^  button:' TOKENS.md` (generated — see below) |
| `src/theme/zocdoc.ts` | ~2600 lines, ~25k tokens | grep for the camelCase group, e.g. `grep -n 'primary: {' -A12` |
| `**/custom-elements.json` | up to 1.3MB generated (package and root manifests) | read the source component, or [`references/index.md`](references/index.md) for the summary |

### Which token file to grep

**`TOKENS.md` to consume a token.** It lists every component token group with the
semantic layer already resolved, so one grep answers what a token evaluates to:

```yaml
button:
  primary:
    bgColor: "{primitive.colors.brand.500}"
```

`zocdoc.ts` would make that a three-hop chase (`button.primary.bgColor` →
`semantic('surface','brand','bgColor')` → `primitive('color','brand',500)`). It
also makes *missing* leaves obvious — `ghost.hover` has no `fgColor`, which is why
`button.styles.ts` gives it a `var(a, var(b))` fallback.

`TOKENS.md` is a **gitignored build artifact**, so a fresh clone does not have it.
If it is missing, generate it — don't fall back to reading `zocdoc.ts`:

```bash
pnpm run build:theme
```

Regeneration is deterministic and takes seconds. It is also the fix when the file
looks out of date: it is not rebuilt on edit, so after changing `zocdoc.ts` rerun
`build:theme` before trusting a value from it.

**`zocdoc.ts` to author a token.** TOKENS.md has no semantic layer, so it cannot
tell you which semantic a new component token should reference — and pointing one
straight at a primitive breaks the layering. Theme edits go in `zocdoc.ts`, then
rerun `build:theme`.

### CSS names appear in neither file

Both are **nested camelCase definitions**. The ~1450 `--zd-*` custom properties
are generated by kebab-casing the path, so the CSS name you see in a stylesheet is
not findable in either source:

```
button.primary.hover.bgColor   ->   --zd-button-primary-hover-bg-color
```

Grep for the path segment (`bgColor`, `primary:`), never the CSS name. The
generated names follow a fixed grammar, so you can guess one and let
`stylesheet-tokens.test.ts` confirm it rather than reading the definition:

```
--zd-<component>-<variant>-<state>-<prop>    --zd-button-primary-hover-bg-color
--zd-<component>-small-<prop>                --zd-button-small-height
--zd-form-control-<prop>                     shared across input/select/text-area/checkbox/radio
```

**Component shape.** All 36 subclass a `Core*` class and append a stylesheet. Only
these deviate, so a component not listed here is styles-only:

| Deviation | Components |
|-----------|-----------|
| `@property` override | alert, badge, button, checkbox, icon, input, radio, text-area |
| `dependencies()` override (17) | accordion-item, alert, breadcrumb-item, button-group-overflow, checkbox, dialog, input, menu, menu-group, menu-item, overflow, push-pane, radio-group, select, switch, text-area, tooltip |
| Template override | alert (`iconTemplate`) — the only one |

**Empty stylesheets are the convention, not an oversight.** 25 of the 36
`*.styles.ts` files are placeholders holding just a comment. They exist so that
adding a Zocdoc override later is a one-line edit rather than a new file plus a
new import, and so the `stylesheet-tokens` test discovers every component. Don't
"clean them up".

## Component Catalog

Generated from the manifest, so it cannot drift. Read the index first, then open the one
component you need — do not read the whole directory.

- [`references/index.md`](references/index.md) — every tag with a one-line summary
- `references/<tag>.md` — one page per component: attributes, properties, events, slots,
  methods, CSS parts, custom properties, states, then everything inherited

One caveat the generated pages cannot express: `zd-select`'s `size` attribute is a `number`
(visible rows, the native `<select>` meaning), not the `'default' | 'small'` control size the
other five form primitives take. See "Size Prop" below.

## Creating a New Primitive

Follow this pattern when adding a component:

```typescript
// src/components/example/example.ts
import CoreExample from '@charm-ux/core/components/example/example.js';
import { project } from '@charm-ux/core';
import styles from './example.styles.js';

/**
 * One sentence saying what the component is for.
 *
 * @tag zd-example
 */
export class ZdExample extends CoreExample {
  static override styles = [...super.styles, styles] as typeof CoreExample.styles;
}

project.scope.registerComponent(ZdExample);
```

`@tag` is load-bearing — there is no `@customElement` decorator, so it is the
only place the manifest learns the tag name. Don't add `@summary`; the first line
of the description serves that purpose.

### With Custom Props

```typescript
import { property } from 'lit/decorators.js';
import type { ZdControlSize } from '../control-size.js';

export type ZdExampleVariant = 'primary' | 'secondary';

export class ZdExample extends CoreExample {
  static override styles = [...super.styles, styles] as typeof CoreExample.styles;

  @property({ reflect: true }) public variant?: ZdExampleVariant;
  @property({ reflect: true }) public size?: ZdControlSize;
}
```

`reflect: true` is not optional here — the stylesheet selects on the attribute
(`:host([variant='primary'])`), so a non-reflecting property renders unstyled.

### With Dependencies Override

When a component renders other primitives, override `dependencies()` so the Zd\*
classes register instead of the Charm originals:

```typescript
/** Mirrors Charm's own dependencies(), swapping each Core* for its Zd* subclass (PBZD-001). */
public static override get dependencies(): (typeof CharmElement)[] {
  return [ZdIcon, ZdButton];
}
```

This override is mechanical: read Charm's own `dependencies()` for that component
and substitute each `Core*` with its `Zd*` subclass. Never add or drop an entry —
a missing one leaves a `ch-*` element in the shadow tree, and an extra one
registers a component the parent never renders.

## Writing Styles

Charm owns structure and state logic. A Zocdoc stylesheet re-points the flat
custom properties Charm already reads, from a `:host(...)` condition:

```css
:host([variant='primary']) {
  --zd-button-bg-color: var(--zd-button-primary-bg-color);
}

:host([size='small']) {
  --zd-button-height: var(--zd-button-small-height);
}
```

Never restate Charm's internals — no `.control:hover`, no `[part]` state
selectors. If Charm renames `.control` or reworks its state logic, a re-pointing
stylesheet keeps working and a restating one silently breaks. `button.styles.ts`
is the worked example, including where a variant's token group is incomplete and
needs a `var(a, var(b))` fallback.

Every `var(--zd-…)` must name a property the theme declares —
`theme/__tests__/stylesheet-tokens.test.ts` discovers all stylesheets by glob and
enforces this. An unresolvable custom property is invalid at computed-value time:
no build error, no console warning, just an unstyled component.

## Theme Tokens

Export from the package:
- `zocdocThemeCss` - All CSS custom properties (~1450 `--zd-*` tokens)
- `zocdocResetCss` - CSS reset
- `zocdocAllCss` - Combined theme + reset + utilities

## Size Prop

Interactive components support `ZdControlSize`:
```typescript
type ZdControlSize = 'default' | 'small';
```

Applies to: `ZdButton`, `ZdCheckbox`, `ZdInput`, `ZdRadio`, `ZdTextArea`.

`ZdIcon` has its own three-step `ZdIconSize` (`small` \| `default` \| `large`).

**`ZdSelect` deliberately has none.** Charm's select already declares
`size?: number` for the native `<select size>` attribute, so the name is taken.
Consumers needing the compact treatment set `--zd-form-control-input-height` and
`--zd-form-control-padding-y` directly.

## Accessibility Tests

One `*.test.ts` per component, running axe in both light and dark mode:

```typescript
import { it } from 'vitest';
import { describeA11y, expectNoViolations, getContainer } from '../../utils/test/a11y.js';

describeA11y('zd-card', () => {
  it('passes axe checks with content', async () => {
    const el = document.createElement('zd-card');
    el.innerHTML = '<p>Card content goes here.</p>';
    getContainer().appendChild(el);

    await expectNoViolations();
  });
});
```

`expectNoViolations()` waits before it reads the document, so **don't call
`waitForUpdate()` immediately before it** — it is redundant. Reach for
`waitForUpdate()` only when a test acts *between* two renders (set a property on
an already-rendered element) or asserts on the DOM itself instead of running axe.
