The client exposes one typed function per API endpoint. Use these to build custom flows or to fetch data outside the components. Parameters are camelCase here and snake_case on the wire. Response objects keep the API's snake_case field names.

For request and response schemas, see the [Zocdoc API Reference](https://api-docs.zocdoc.com/apis). For how the calls fit together, see [Find Provider Availability and Book Appointments](https://api-docs.zocdoc.com/guides/patient/book-appointments).

## Provider Search

### searchProviderLocations

`GET /v1/provider_locations`: search for provider locations near a ZIP code.

```typescript
import { searchProviderLocations } from '@zocdoc/api-components';

const result = await searchProviderLocations({
  zipCode: '11201',
  specialtyId: 'sp_153',
  insurancePlanId: 'ip_9111',
});

// result.providerLocations: ProviderLocation[]
// result.totalCount: number
// result.pageSize: number
// result.searchParameters: the filters the API applied, including defaults
```

| Name | Type | Required | Description |
|------|------|----------|-------------|
| `zipCode` | `string` | Yes | 5-digit ZIP code. The API has no "search everywhere" mode |
| `specialtyId` | `string` | No | Filter by specialty |
| `visitReasonId` | `string` | No | Filter by visit reason |
| `insurancePlanId` | `string` | No | Only providers in-network for this plan |
| `visitType` | `'all' \| 'in_person' \| 'video_visit'` | No | In-person, video, or both |
| `maxDistanceToPatientMi` | `number` | No | Search radius in miles |
| `page` | `number` | No | Zero-based page index |
| `pageSize` | `number` | No | Results per page (default: `DEFAULT_PAGE_SIZE`, 10) |

A search that matches nothing resolves with an empty `providerLocations` array. It doesn't throw.

Some provider locations include `booking_requirements`, such as insurance member and plan IDs that are required to book. Check these before collecting patient details.

## Availability

### getAvailability

`GET /v1/provider_locations/availability`: open timeslots for one or more provider locations.

```typescript
import { getAvailability } from '@zocdoc/api-components';

const entries = await getAvailability({
  providerLocationIds: ['pr_abc|lo_xyz'],
  visitReasonId: 'pc_FRO-18leckytNKtruw5dLR',
  patientType: 'new',
  startDate: '2026-10-07',
  endDate: '2026-10-13',
});

// entries: ProviderLocationAvailability[], one per requested location
// entries[0].timeslots: AvailabilitySlot[] (always an array, possibly empty)
```

| Name | Type | Required | Description |
|------|------|----------|-------------|
| `providerLocationIds` | `string[]` | Yes | `pr_…\|lo_…` IDs, passed through unchanged. Batch several locations in one call |
| `visitReasonId` | `string` | Yes | Availability differs by visit reason |
| `patientType` | `'new' \| 'existing'` | Yes | Availability differs for new and existing patients |
| `startDate` | `string` | No | `YYYY-MM-DD` in provider local time. Defaults to today |
| `endDate` | `string` | No | `YYYY-MM-DD`. Defaults to 7 days after the start, and must be within 30 days of it |
| `insurancePlanId` | `string` | No | Insurance plan ID |
| `insuranceCarrierId` | `string` | No | Insurance carrier ID |

<Aside>
  The API rejects windows longer than 30 days, and Zocdoc guarantees availability only up to 150 days out. The client exports the 30-day limit as `MAX_AVAILABILITY_DAYS` so you can clamp windows to it.
</Aside>

## Appointments

### createAppointment

`POST /v1/appointments`: book a timeslot.

```typescript
import { createAppointment } from '@zocdoc/api-components';

const appointment = await createAppointment({
  providerLocationId: 'pr_abc|lo_xyz',
  visitReasonId: 'pc_FRO-18leckytNKtruw5dLR',
  startTime: slot.start_time, // Exactly as returned by getAvailability
  patientType: 'new',
  patient: {
    first_name: 'Test',
    last_name: 'Patient',
    date_of_birth: '1990-01-15',
    sex_at_birth: 'female',
    phone_number: '2125550001',
    email_address: 'test@example.com',
    patient_address: {
      address1: '1 Test St',
      city: 'Brooklyn',
      state: 'NY',
      zip_code: '11201',
    },
    insurance: { is_self_pay: true },
  },
});

// appointment.appointment_id: string
// appointment.appointment_status: 'confirmed' | 'pending_booking' | 'booking_failed' | ...
```

| Name | Type | Required | Description |
|------|------|----------|-------------|
| `providerLocationId` | `string` | Yes | Provider location ID |
| `visitReasonId` | `string` | Yes | Visit reason ID |
| `startTime` | `string` | Yes | A `start_time` from `getAvailability`, unchanged, offset included |
| `patientType` | `'new' \| 'existing'` | Yes | Must match the availability you searched |
| `patient` | `Patient` | Yes | Patient details. Every field is PHI |
| `notes` | `string` | No | Patient-written note, maximum 100 characters. Also PHI |

`phone_number` must be 10 digits with no formatting, and the 1st and 4th digits can't be `0` or `1`.

<Aside type="caution">
  A resolved promise doesn't mean a confirmed appointment. Check `appointment_status`, since `pending_booking` and `booking_failed` both arrive on a successful response. See [Booking Failures on a Success Status](/zocdoc-api-components/client/errors/#booking-failures-on-a-success-status).
</Aside>

Use `appointment_id` to reschedule or cancel. See Zocdoc's [Reschedule](https://api-docs.zocdoc.com/guides/patient/reschedule-appointments) and [Cancel](https://api-docs.zocdoc.com/guides/patient/cancel-appointments) guides. The client doesn't wrap those endpoints yet. To hear about status changes, such as a pending booking becoming confirmed, subscribe your backend to Zocdoc [Webhooks](https://api-docs.zocdoc.com/guides/webhooks).

## Reference Data

Specialties, visit reasons, and insurance plans supply the IDs the other endpoints take. See Zocdoc's [Reference Data](https://api-docs.zocdoc.com/guides/reference-data) guide. Each function fetches every page and returns the complete list.

### getSpecialties

`GET /v1/specialties`

```typescript
import { getSpecialties } from '@zocdoc/api-components';

const specialties = await getSpecialties();
// [{ id: 'sp_153', name: 'Primary Care Doctor', default_visit_reason_id: '…', ... }, ...]
```

### getVisitReasons

`GET /v1/visit_reasons`, optionally filtered by specialty:

```typescript
import { getVisitReasons } from '@zocdoc/api-components';

const reasons = await getVisitReasons('sp_153');
// [{ id: 'pc_FRO-18leckytNKtruw5dLR', name: 'New patient visit', specialty_id: 'sp_153' }, ...]
```

### getInsurancePlans

`GET /v1/insurance_plans`, with optional filters:

```typescript
import { getInsurancePlans } from '@zocdoc/api-components';

const plans = await getInsurancePlans({ state: 'NY', careCategory: 'health' });
```

| Filter | Type | Description |
|---|---|---|
| `state` | `string` | Two-letter code. Returns plans whose coverage includes the state |
| `careCategory` | `'health' \| 'dental' \| 'vision'` | Plan category |
| `networkType` | `string` | Network type |
| `programType` | `InsuranceProgramType` | For example, `commercial` or `medicare` |
| `status` | `'active' \| 'inactive' \| 'deleted'` | Defaults to `active` on the server |

<Aside type="caution">
  Always filter where you can. The unfiltered production list has more than 10,000 plans. That's dozens of requests and megabytes of JSON to fill one dropdown. `state` is the natural filter for a booking flow.
</Aside>

## Caching

Reference data is cached in memory for the page lifetime. Each distinct set of filters gets its own cache entry. Concurrent callers share one in-flight request, and a failed request isn't cached, so the next call retries.

```typescript
const a = await getSpecialties(); // Network request
const b = await getSpecialties(); // Cached
```

To force a refresh, for example after switching between sandbox and production, call `clearReferenceDataCache()`.

Provider search and availability aren't cached, because they change constantly.
