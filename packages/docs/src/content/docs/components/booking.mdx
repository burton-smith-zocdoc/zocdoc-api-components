The `<zd-booking>` component orchestrates the entire booking flow: provider search, availability selection, patient form, and confirmation.

## Usage

```html preview
<zd-booking
  modal
  zip-code="11201"
  insurance-plan-id="ip_9111"
></zd-booking>
```

## Examples

### Inline Mode

Render the booking flow inline rather than in a modal:

```html preview
<zd-booking
  zip-code="11201"
></zd-booking>
```

### Starting Partway

The current step is worked out from the properties you've set, so you can start the flow later in by setting them:

- Set `providers` (with `total-count`) to start at a results list from your own search.
- Set `provider-location-id` to skip to the time step.
- Set `start-time` as well to skip to the patient form.

```html
<zd-booking
  modal
  provider-location-id="pr_confirmed|lo_confirmed"
  visit-reason-id="pc_FRO-18leckytNKtruw5dLR"
></zd-booking>
```

Read the current step from the `step` property (`'search' | 'time' | 'patient' | 'booked'`). It can't be set directly, and there's no step-change event.

## Attributes

| Attribute | Type | Default | Description |
|-----------|------|---------|-------------|
| `modal` | `boolean` | `false` | Run the steps after the search in a dialog over the results |
| `hide-photos` | `boolean` | `false` | Hide provider photos |
| `zip-code` | `string` | — | ZIP code the search opens on |
| `specialty-id` | `string` | — | Specialty the search opens on |
| `visit-reason-id` | `string` | — | Visit reason. If unset, falls back to the reason the search resolved, then to the provider's default |
| `insurance-plan-id` | `string` | — | Insurance plan. Filters the search and is sent with the booking. See [Insurance](#insurance) |
| `insurance-name` | `string` | — | Display name of the plan, for the network status line |
| `patient-type` | `'new' \| 'existing'` | `'new'` | Which slots are bookable. Kept in sync with the picker's toggle |
| `page` | `number` | `0` | Zero-based results page |
| `page-size` | `number` | `10` | Results per page |
| `total-count` | `number` | — | Total matches, for the count and pager when you set `providers` yourself |
| `provider-location-id` | `string` | — | Chosen `pr_…\|lo_…`. Setting it moves to the time step |
| `start-time` | `string` | — | Chosen slot's `start_time`, exactly as returned. Setting it moves to the patient form |

`providers` (`ProviderLocation[]`) is a property only.

## Insurance

`<zd-booking>` passes `insurance-plan-id` and the selected location's `booking_requirements.required_fields` to the patient form. When a location requires a member ID, the form asks for one. When it requires a plan and none was chosen, the form asks the patient to go back and choose one. See [Patient Form: Insurance](/zocdoc-api-components/components/patient-form/#insurance).

## Methods

| Method | Description |
|---|---|
| `book(patient, notes?)` | Book the chosen slot. Use this if you collect patient details yourself. Does nothing while a booking is in flight |

## Events

| Event | Detail | Description |
|-------|--------|-------------|
| `booking-complete` | `{ appointmentId, status }` | The API took the appointment. `status` is `confirmed` or `pending_booking`. Word these differently to the patient |
| `booking-error` | `{ error, status? }` | Booking didn't happen. `status` is set when the API returned `200` with a status that isn't a booking, such as `booking_failed` |
| `availability-error` | `{ error }` | The batched availability request for the results list failed. Nothing is rendered for it, and the list still works without day counts |

Events from the child components (`provider-select`, `slot-select`, `patient-submit`, and others) bubble out of `<zd-booking>` too, so you can observe them. See [Hybrid Approach](/zocdoc-api-components/guides/composed-vs-single/#hybrid-approach).

<Aside type="danger">
  `detail.error` is the client's error. Its body can echo submitted patient fields, so never log or render it.
</Aside>

## Zocdoc API

Runs Zocdoc's full [availability search and booking flow](https://api-docs.zocdoc.com/guides/patient/book-appointments): reference data, provider search, availability, then `POST /v1/appointments`. A successful request can still return `pending_booking`, which emits `booking-complete`, or `booking_failed`, which emits `booking-error`. In the sandbox, the booked provider location determines the status. See [Test Scenarios](/zocdoc-api-components/guides/testing/#test-scenarios) and the [Zocdoc API overview](/zocdoc-api-components/guides/zocdoc-api/).

## Accessibility

- Focus moves to the new step's heading container on every step change
- In `modal` mode, the dialog traps focus and returns it on close
- A live region announces a booking in flight, and booking failures use an alert
- All form fields have visible labels

## Styling

Style the flow through CSS parts:

| Part | Description |
|---|---|
| `step` | The current step's container (inline mode) |
| `step-heading` | The current step's heading |
| `dialog` | The dialog, in `modal` mode |
| `modal-step` | The current step's container inside the dialog |
| `back` | The back button |
| `summary` | The block restating what is about to be booked |
| `status` | Live region announcing a booking in flight |
| `error` | The alert shown when a booking fails |
| `search`, `results`, `picker`, `patient-form`, `confirmation` | The child components |
