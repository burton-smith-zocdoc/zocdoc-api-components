The `<zd-booking>` component orchestrates the entire booking flow: provider search, availability selection, patient form, and confirmation.

## Usage

```html preview
<zd-booking modal zip-code="11201" insurance-plan-id="ip_9111"></zd-booking>
```

## Examples

### Inline Mode

Render the booking flow inline rather than in a modal:

```html preview
<zd-booking zip-code="11201"></zd-booking>
```

### Starting Partway

The current step is worked out from the properties you've set, so you can start the flow later in by setting them:

- Set `providers` (with `total-count`) to start at a results list from your own search.
- Set `provider-location-id` to skip to the time step.
- Set `start-time` as well to skip to the patient form.

```html
<zd-booking
  modal
  provider-location-id="pr_confirmed|lo_confirmed"
  visit-reason-id="pc_FRO-18leckytNKtruw5dLR"
></zd-booking>
```

Read the current step from the `step` property (`'search' | 'time' | 'patient' | 'booked'`). It can't be set directly, and there's no step-change event.

## Insurance

`<zd-booking>` passes `insurance-plan-id` and the selected location's `booking_requirements.required_fields` to the patient form. When a location requires a member ID, the form asks for one. When it requires a plan and none was chosen, the form asks the patient to go back and choose one. See [Patient Form: Insurance](/zocdoc-api-components/components/patient-form/#insurance).

## Handling Events

Events from the child components (`provider-select`, `slot-select`, `patient-submit`, and others) bubble out of `<zd-booking>` too, so you can observe them. See [Hybrid Approach](/zocdoc-api-components/guides/composed-vs-single/#hybrid-approach).

<Aside type="danger">
  `detail.error` is the client's error. Its body can echo submitted patient fields, so never log or
  render it.
</Aside>

## Zocdoc API

Runs Zocdoc's full [availability search and booking flow](https://api-docs.zocdoc.com/guides/patient/book-appointments): reference data, provider search, availability, then `POST /v1/appointments`. A successful request can still return `pending_booking`, which emits `booking-complete`, or `booking_failed`, which emits `booking-error`. In the sandbox, the booked provider location determines the status. See [Test Scenarios](/zocdoc-api-components/guides/testing/#test-scenarios) and the [Zocdoc API overview](/zocdoc-api-components/guides/zocdoc-api/).

## Accessibility

- Focus moves to the new step's heading container on every step change
- In `modal` mode, the dialog traps focus and returns it on close
- A live region announces a booking in flight, and booking failures use an alert
- All form fields have visible labels
