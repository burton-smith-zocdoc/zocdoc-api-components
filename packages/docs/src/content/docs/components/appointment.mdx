The `<zd-appointment>` component loads a booked appointment by its ID, shows its status and time, and lets the patient cancel it or move it to a new time.

## Usage

```html preview
<zd-appointment appointment-id="d2ee5bd8-643a-42c8-8c5a-be450e903430"></zd-appointment>
```

The example uses the sandbox's confirmed appointment ID. In the docs it runs against the mock, which doesn't store anything, so a cancelled appointment comes back confirmed when you reload.

## Provider and Practice Details

The component looks up the provider by the appointment's `provider_location_id` and shows their photo, name, specialty, and address. If that lookup fails, the appointment still shows: the Provider row falls back to `provider-name`, or is left out. No error appears and no `appointment-error` event fires, because the appointment itself loaded.

The details also show the practice's phone number from `location_phone_number`, as a link that dials it, extension included. For a Zocdoc video visit they add a link to `waiting_room_path`, which opens in a new tab. The link only appears for an absolute `https:` URL, and not for a cancelled, failed, or missed appointment, since there's no visit left to join. Each row is left out when the appointment doesn't include its field.

## What Patients Can Do

The appointment's status decides which actions appear:

| Status                                                              | Change time | Cancel |
| ------------------------------------------------------------------- | ----------- | ------ |
| `confirmed`, `pending_booking`, `pending_reschedule`, `rescheduled` | Yes         | Yes    |
| `reschedule_failed`                                                 | No          | Yes    |
| `booking_failed`, `cancelled`, `no_show`                            | No          | No     |

"Change time" also requires the lookup to return `patient_type`. A reschedule keeps the original location, visit reason, and patient type, so the component shows times only for those. Without the patient type it can't tell which times the API will accept.

Cancelling asks for confirmation first, with an optional reason.

## Cancelling and Rescheduling

`cancel()` and `reschedule(startTime)` are listed under [API Reference](#api-reference). While one action is in flight, a second call does nothing. Neither action retries by itself.

## Zocdoc API

| Action      | Endpoint                                                                           | Scope                        |
| ----------- | ---------------------------------------------------------------------------------- | ---------------------------- |
| Look up     | `GET /v1/appointments/{appointment_id}`                                            | `external.appointment.read`  |
| Provider    | `GET /v1/provider_locations/{provider_location_id}`                                | Any                          |
| Cancel      | `POST /v1/appointments/cancel`                                                     | `external.appointment.write` |
| Change time | `GET /v1/provider_locations/availability`, then `POST /v1/appointments/reschedule` | `external.appointment.write` |

An appointment booked with a user credential can only be viewed or changed by that user. Machine-to-machine credentials can reach any appointment booked by the developer's machine-to-machine credentials. If cancel returns `409` because the appointment changed elsewhere, the component fetches its current status without leaving the details view, and says it can no longer be cancelled.

See Zocdoc's [Cancel](https://api-docs.zocdoc.com/guides/patient/cancel-appointments) and [Reschedule](https://api-docs.zocdoc.com/guides/patient/reschedule-appointments) guides.

## Supplied Data

A page that already has the appointment, such as an MCP server, sets `appointment` by script. From then on the component makes no appointment calls. It still looks up the provider unless you also set `providerLocation`. Cancel and reschedule emit `appointment-cancel-request` and `appointment-reschedule-request`, say "Cancelling your appointment…" or "Changing your appointment time…", and wait for you to set the updated `appointment`, or `actionError` when the action failed. Opening reschedule emits `availability-request`, answered by setting `rescheduleTimeslots`.

A reschedule counts as done when the updated appointment is at the chosen time, or is `pending_reschedule`. Setting an appointment with a different `appointment_id` drops any action waiting for an answer, and asks for reschedule times again unless you set `rescheduleTimeslots` with it.

Set `actionError` to any string each time an action fails, even the same one as last time. You never have to clear it. The component shows its own message and emits `appointment-error` with the action, never your text. The appointment is never read from markup, because it's patient data. See [Markup and Supplied Data](/zocdoc-api-components/guides/markup-and-supplied-data/).

## Accessibility

- Loading and errors use the same live regions as the other components
- An action in flight and a completed action are both announced through a polite status region
- A failed action is announced as an alert
- Focus moves to the panel on each change between viewing, cancelling, and choosing a time
