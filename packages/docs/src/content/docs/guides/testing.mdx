You can test an integration two ways:

- **Mock transport.** No network and no token. Use it for unit tests, demos, and local development.
- **Zocdoc sandbox.** Real API calls against `https://api-developer-sandbox.zocdoc.com` with sandbox credentials. The sandbox comes pre-populated with sample reference data.

Both respond to the same sentinel inputs from Zocdoc's [API Endpoint Test Scenarios](https://api-docs.zocdoc.com/guides/testing-data) guide. A test written against the mock exercises the same states the sandbox would return.

## Mock Transport

```javascript
import { configureZocdocMock } from '@zocdoc/api-components/mock';

configureZocdocMock();
```

This replaces the network call with a transport that serves fixture data. Components work exactly as they do live. Nothing is stored: submitted patient details are checked and then discarded.

| Option | Default | Description |
|---|---|---|
| `latencyMs` | `300` | Delay per request, so loading states are visible |
| `availabilityStartDate` | Requested start, or today | Pins the first day of generated availability. Use it for stable snapshots |
| `assetBaseUrl` | Origin root | Prefix for fixture photo paths when the host is served under a sub-path |

To build your own `configureZocdoc` call around the mock (for example, alongside a different `baseUrl`), use `createMockTransport(options)` as the `transport` option.

## Test Scenarios

The sentinel values are exported as `SCENARIOS`, so tests don't hard-code them:

```javascript
import { configureZocdocMock, SCENARIOS } from '@zocdoc/api-components/mock';
```

### Provider search (`GET /v1/provider_locations`)

| Input | `SCENARIOS` key | Result |
|---|---|---|
| `zip_code=11201` | `zipWithResults` | Provider locations, some with booking requirements |
| `zip_code=99734` | `zipEmpty` | No provider locations (empty state) |
| `zip_code=10112` | `zipError` | `500` error |
| `insurance_plan_id=ip_0` | `insurancePlanMissing` | `400` invalid plan |

### Availability (`GET /v1/provider_locations/availability`)

| Provider location ID | `SCENARIOS` key | Result |
|---|---|---|
| `pr_no_availbility\|lo_no_availbility` | `providerLocationNoAvailability` | No open timeslots |
| `pr_error\|lo_error` | `providerLocationError` | `500` error |

<Aside type="note">
  `no_availbility` is misspelled in Zocdoc's guide, and the sandbox matches the misspelled value. Use it as written.
</Aside>

### Booking (`POST /v1/appointments`)

The `provider_location_id` you book determines the returned `appointment_status`:

| Provider location ID | `SCENARIOS` key | Result |
|---|---|---|
| `pr_confirmed\|lo_confirmed` | `providerLocationConfirmed` | `confirmed` |
| `pr_pending\|lo_pending` | `providerLocationPending` | `pending_booking` |
| `pr_bookingfailed\|lo_bookingfailed` | `providerLocationBookingFailed` | `booking_failed` |
| `pr_cancelled\|lo_cancelled` | `providerLocationCancelled` | `cancelled` |
| `pr_noshow\|lo_noshow` | `providerLocationNoShow` | `no_show` |
| `pr_pendingreschedule\|lo_pendingreschedule` | `providerLocationPendingReschedule` | `pending_reschedule` |
| `pr_rescheduled\|lo_rescheduled` | `providerLocationRescheduled` | `rescheduled` |
| `pr_reschedulefailed\|lo_reschedulefailed` | `providerLocationRescheduleFailed` | `reschedule_failed` |
| `pr_insuranceIdIsRequired\|lo_insuranceIdIsRequired` | `providerLocationInsuranceRequired` | `400` unless insurance plan and member IDs are sent |
| `pr_selfPayNotAccepted\|lo_selfPayNotAccepted` | `providerLocationSelfPayNotAccepted` | `400` when `is_self_pay` is `true` |
| `pr_acceptsInNetworkOnly\|lo_acceptsInNetworkOnly` | `providerLocationInNetworkOnly` | `400` when an insurance plan is supplied |
| `pr_error\|lo_error` | `providerLocationError` | `500` error |

In the mock, any other location confirms. Zocdoc's guide also documents sandbox scenarios for endpoints these components don't call yet, including `/v1/providers` by NPI, facilities, insurance mappings, cancel, and reschedule.

### Insurance plans

The guide's insurance plan IDs work as filter values. Examples: `ip_9111` (active), `ip_2667` (inactive), `ip_5432` (national coverage), `ip_2345` (California coverage), `ip_2052` (Medicare), and `ip_8281` (Medicaid). Filtering `GET /v1/insurance_plans` by state `AK` returns an empty list.

## Example

```javascript
import { configureZocdocMock, SCENARIOS } from '@zocdoc/api-components/mock';
import '@zocdoc/api-components';

describe('provider search', () => {
  beforeEach(() => {
    configureZocdocMock({ latencyMs: 0 });
  });

  it('shows providers for a ZIP with results', async () => {
    const el = document.createElement('zd-provider-search');
    el.zipCode = SCENARIOS.zipWithResults;
    document.body.appendChild(el);
    // Trigger search and verify results appear
  });

  it('shows the empty state, not an error, when nothing matches', async () => {
    const el = document.createElement('zd-provider-search');
    el.zipCode = SCENARIOS.zipEmpty;
    document.body.appendChild(el);
    // Verify empty state renders
  });

  it('shows the error state on a server error', async () => {
    const el = document.createElement('zd-provider-search');
    el.zipCode = SCENARIOS.zipError;
    document.body.appendChild(el);
    // Verify error state renders and `provider-search-error` fires
  });
});
```

## Test Patient Data

Patient details are PHI in production. In tests, use obviously fake values. Never use real-looking names, phone numbers, or addresses:

| Field | Test Value |
|-------|------------|
| `first_name` | `Test` |
| `last_name` | `Patient` |
| `date_of_birth` | `1990-01-15` |
| `phone_number` | `2125550001` (10 digits; the 1st and 4th digits can't be 0 or 1) |
| `email_address` | `test@example.com` |

## Component Testing

Each component renders from properties, so you can test it in isolation without any API at all:

```javascript
import '@zocdoc/api-components';

it('renders a provider card', async () => {
  const card = document.createElement('zd-provider-card');
  card.provider = providerLocationFixture; // A ProviderLocation from your own fixtures
  document.body.appendChild(card);
  await card.updateComplete;

  expect(card.shadowRoot.textContent).toContain('Test Provider');
});
```

## Accessibility Testing

All components pass axe-core. Check more than the default state: include loading, empty, and error states too:

```javascript
import { axe, toHaveNoViolations } from 'jest-axe';

expect.extend(toHaveNoViolations);

it('has no accessibility violations', async () => {
  const el = document.createElement('zd-provider-card');
  el.provider = providerLocationFixture;
  document.body.appendChild(el);

  const results = await axe(el);
  expect(results).toHaveNoViolations();
});
```
