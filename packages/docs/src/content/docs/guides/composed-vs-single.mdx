## Two Approaches

You can integrate Zocdoc API Components in two ways:

1. **Single element** — Use `<zd-booking>` for the complete flow in one tag
2. **Composed** — Wire individual components together for custom layouts and behavior

## Single Element

The `<zd-booking>` component handles the entire booking funnel:

```html preview
<zd-booking
  modal
  zip-code="11201"
></zd-booking>
```

**Pros:**
- Zero wiring required
- Handles all state transitions
- One event to handle (`booking-complete`)

**Cons:**
- Fixed layout and flow
- Limited customization points
- All-or-nothing

**Best for:** Quick integrations, standard booking flows, proof of concepts.

## Composed Flow

For custom layouts, wire the components yourself:

```html
<zd-provider-search
  id="search"
  zip-code="11201"
></zd-provider-search>

<zd-provider-results
  id="results"
></zd-provider-results>

<zd-availability-picker
  id="picker"
  style="display: none;"
></zd-availability-picker>

<zd-patient-form
  id="form"
  style="display: none;"
></zd-patient-form>

<zd-booking-confirmation
  id="confirmation"
  style="display: none;"
></zd-booking-confirmation>
```

Then handle the events. Each component renders from properties and reports back through events. Your code passes data between them and makes the booking call:

```javascript
import { createAppointment } from '@zocdoc/api-components';

const search = document.getElementById('search');
const results = document.getElementById('results');
const picker = document.getElementById('picker');
const form = document.getElementById('form');
const confirmation = document.getElementById('confirmation');

let provider;
let visitReasonId;
let startTime;
let patientType = 'new';
let insurancePlanId;

// Search emits one page of results
search.addEventListener('provider-results', (e) => {
  results.providers = e.detail.providers;
  results.totalCount = e.detail.totalCount;
  results.page = e.detail.page;
  results.pageSize = e.detail.pageSize;
  insurancePlanId = e.detail.insurancePlanId;
  visitReasonId = e.detail.searchParameters?.visit_reason_id;
});

// Paging: the search refetches when its page changes
results.addEventListener('page-change', (e) => {
  search.page = e.detail.page;
});

// Results emit the chosen provider location; the picker fetches its own times
results.addEventListener('provider-select', (e) => {
  provider = e.detail.provider;
  visitReasonId ??= provider.provider.default_visit_reason_id;
  picker.providerLocationId = provider.provider_location_id;
  picker.visitReasonId = visitReasonId;
  picker.patientType = patientType;
  picker.style.display = 'block';
});

picker.addEventListener('patient-type-change', (e) => {
  patientType = e.detail.patientType;
});

// Picker emits the chosen slot
picker.addEventListener('slot-select', (e) => {
  startTime = e.detail.startTime;
  // Lets the form ask for what this location requires, such as an insurance member ID
  form.insurancePlanId = insurancePlanId;
  form.requiredFields = provider.booking_requirements?.required_fields ?? [];
  form.style.display = 'block';
});

// Form emits patient details. These are PHI: send them only to createAppointment, never log them
form.addEventListener('patient-submit', async (e) => {
  form.busy = true;
  try {
    const appointment = await createAppointment({
      providerLocationId: provider.provider_location_id,
      visitReasonId,
      startTime,
      patientType,
      patient: e.detail.patient,
      notes: e.detail.notes,
    });

    // A resolved request isn't always a booking
    if (appointment.appointment_status === 'booking_failed') {
      showBookingFailed(); // Your own message. Suggest choosing another time
      return;
    }

    confirmation.appointmentId = appointment.appointment_id;
    confirmation.status = appointment.appointment_status;
    confirmation.startTime = startTime;
    confirmation.providerName = provider.provider.full_name;
    confirmation.style.display = 'block';
  } catch (error) {
    showBookingFailed(); // Never show error.message or error.body to the patient
  } finally {
    form.busy = false;
  }
});
```

`<zd-booking>` also handles things this example doesn't: batched day counts on the results, Back buttons, focus management between steps, and every `appointment_status`. See [Booking Failures on a Success Status](/zocdoc-api-components/client/errors/#booking-failures-on-a-success-status).

**Pros:**
- Full control over layout
- Custom step order and logic
- Insert your own UI between steps

**Cons:**
- More code to write and maintain
- You handle error states
- You manage visibility and transitions

**Best for:** Custom designs, multi-step wizards, embedded in existing flows.

## Hybrid Approach

You can also use `<zd-booking>` and intercept events to inject custom behavior:

```javascript
const booking = document.querySelector('zd-booking');

booking.addEventListener('provider-select', (e) => {
  // Log analytics, show a custom modal, etc.
  trackEvent('provider_selected', { providerLocationId: e.detail.provider.provider_location_id });
});
```

Child events bubble out of `<zd-booking>`'s shadow DOM, and `<zd-booking>` continues the flow. You're just observing. Log IDs and actions only. Never log `patient-submit` details, which are PHI.
